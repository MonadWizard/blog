## ভূমিকা / সৎ প্রেক্ষাপট

এই পোস্ট নিজে কোনো টিউটোরিয়াল না — এটা [**Git মাস্টারি জার্নি**](/journey/git-mastery-journey)-র ম্যাপ। আসল কনটেন্ট (৩১৬টা ডিটেইলড লিফ, প্রতিটাতে ইন্টারনাল মেকানিজম + বাস্তব উদাহরণ + কোড) journey পাতাতেই আছে। এখানে শুধু বোঝানো হচ্ছে কী কী আছে, কোন অর্ডারে পড়বেন, আর কোন অংশটা আপনার এখন সবচেয়ে বেশি দরকার।

**এই কারিকুলাম কী গ্যারান্টি দেয় না:**
- এটা পড়লেই আপনি "গিট এক্সপার্ট" হয়ে যাবেন না — শুধু পড়া আর হাতে-কলমে করে দেখা এক জিনিস না। প্রতিটা মডিউলের ল্যাব (⭐) নিজে টার্মিনালে করে দেখুন।
- এটা কোনো নির্দিষ্ট GUI টুল (SourceTree, GitKraken) বা নির্দিষ্ট hosting platform (GitLab, Bitbucket)-এর স্ক্রিনশট-বেসড গাইড না — Git কমান্ড-লাইন আর তার ইন্টারনালস-কেন্দ্রিক।

**কেন এত গভীরে যাওয়া দরকার:** বেশিরভাগ ডেভেলপার Git-কে ৮-১০টা মুখস্থ কমান্ডের সেট হিসেবে ব্যবহার করেন — `add`, `commit`, `push`, `pull`, আর ভয় পেলে `git status` বারবার। কিন্তু যখন একটা `rebase` মাঝপথে আটকে যায়, বা `reset --hard` করার পর কাজ হারিয়ে যায়, বা একটা leaked secret কমিট হয়ে যায় — তখন মুখস্থ কমান্ড আর কাজ করে না। internals (object model, ref model, index) বুঝলে প্রতিটা এমার্জেন্সি সিনারিওই আসলে যুক্তিসঙ্গত, সমাধানযোগ্য একটা পাজল হয়ে যায়।

> এই কারিকুলাম নিয়ে আরও context: ব্লগে আগে থেকেই থাকা [**গিট সিনারিও এবং তার সমাধান**](/blog/2026-07-06-গিট-git-সিনারিও-এবং-তার-সমাধান) পোস্টটা একটা quick-reference (১০০টা সিনারিও → সমাধান)। এই জার্নি সেটার চেয়ে অনেক গভীর, structured, আর ইন্টারনালস-ফোকাসড — দুইটা একসাথে ব্যবহার করুন।

## এই গাইড কীভাবে ব্যবহার করবেন

Journey পাতায় প্রতিটা মডিউলের ভেতরে একই প্যাটার্নের কয়েকটা লেয়ার থাকে:

| লেয়ার | কী পাবেন |
|---|---|
| **What / How / Why** | কনসেপ্ট বা কমান্ড কী, ভেতরে কীভাবে কাজ করে (object/ref/index মডেল), আর কেন দরকার — বাস্তব উদাহরণসহ |
| **Do (ল্যাব)** ⭐ | নিজে টার্মিনালে করার জন্য একটা স্টেপ-বাই-স্টেপ হ্যান্ডস-অন এক্সারসাইজ |
| **পরীক্ষা** | ৪-৬টা ইন্টারভিউ-স্টাইল প্রশ্ন-উত্তর, ঐ মডিউলের টপিক নিয়ে |
| **কর্নার কেস** | ঐ মডিউলের কমান্ডগুলোর সবচেয়ে কমন গোচরা/ফুটগান, আর তার ফিক্স |

কিছু মডিউলের শেষে একটা **🔑 চেকপয়েন্ট** (gate) leaf থাকে — এটা একটা "আপনি কি সত্যিই পারবেন?" self-check, পরের Phase-এ যাওয়ার আগে। এগুলো এড়িয়ে না গিয়ে সত্যিকারের সেলফ-টেস্ট হিসেবে ব্যবহার করুন।

**সাজেস্টেড অর্ডার:** Phase ০ থেকে ১২ পর্যন্ত ক্রমানুসারে পড়াই সবচেয়ে ভালো — বিশেষ করে **Phase 2 (Git Internals)** স্কিপ করবেন না, কারণ Phase 3-এর পর থেকে প্রায় প্রতিটা ব্যাখ্যাই object/ref/index মডেলের টার্মে করা। যদি আপনি ইতিমধ্যে দৈনন্দিন Git ব্যবহারে comfortable, তাহলে সরাসরি Phase 2 থেকে শুরু করে Phase 12 পর্যন্ত পড়তে পারেন — Phase 0-1 আপনার জন্য রিক্যাপ হবে মাত্র।

## গেট/চেকপয়েন্ট তালিকা

জার্নিতে মোট ৬টা 🔑 gate checkpoint আছে — প্রতিটা একটা মেজর মাইলস্টোন শেষে:

1. **Module 7 শেষে (Phase 2)** — Object model/refs/index সত্যিই বোঝা হয়েছে কিনা যাচাই।
2. **Module 16 শেষে (Phase 4)** — "Undo মাস্টারি" — reflog দিয়ে যেকোনো ভুল থেকে রিকভার করার আত্মবিশ্বাস।
3. **Module 27 শেষে (Phase 8)** — বড় repo/monorepo টুলিং-এ স্বচ্ছন্দ কিনা।
4. **Module 33 শেষে (Phase 10)** — সিকিউরিটি হাইজিন অভ্যাসে পরিণত হয়েছে কিনা।
5. **Module 37 শেষে (Phase 11)** — GitHub টিম-ওয়ার্কফ্লো (fork/PR/protection/Actions) মিলিয়ে।
6. **Module 39 — চূড়ান্ত ক্যাপস্টোন (Phase 12)** — একটা সিমুলেটেড ক্রাইসিস-উইক রিপোতে conflict + rebase + reflog + secret removal + governed PR merge সব একসাথে।

## Appendix A — সম্পূর্ণ কমান্ড চিটশিট

জার্নির প্রতিটা কমান্ড বিস্তারিতভাবে নিজের leaf-এ কভার করা আছে; এখানে শুধু ক্যাটাগরি-বাই-ক্যাটাগরি একটা কম্প্যাক্ট ইনডেক্স:

| ক্যাটাগরি | প্রতিনিধিত্বমূলক কমান্ড | কোথায় বিস্তারিত |
|---|---|---|
| সেটআপ ও কনফিগ | `init`, `clone`, `config`, `includeIf` | Phase 0 |
| স্টেজিং ও কমিট | `add -p`, `status -s`, `restore`, `commit --amend` | Phase 1 |
| প্লাম্বিং / অবজেক্ট মডেল | `hash-object`, `cat-file`, `write-tree`, `commit-tree`, `update-ref` | Phase 2 |
| ব্রাঞ্চিং | `branch`, `switch -c`, `switch --detach/--orphan` | Phase 3 |
| মার্জ/রিবেস/আন্ডু | `merge --no-ff`, `rebase -i`, `reset --soft/--mixed/--hard`, `revert`, `cherry-pick`, `reflog` | Phase 4 |
| রিমোট | `remote`, `fetch -p`, `pull --rebase`, `push --force-with-lease` | Phase 5 |
| হিস্ট্রি/ফরেনসিক্স | `log -S/-G/--graph`, `show`, `blame -w`, `bisect run` | Phase 6 |
| ট্যাগ ও স্ট্যাশ | `tag -a -s`, `stash push -p`, `stash branch` | Phase 7 |
| ওয়ার্কস্পেস টুলস | `worktree add`, `submodule update`, `sparse-checkout set`, `lfs track` | Phase 8 |
| কাস্টমাইজেশন | `alias`, `check-ignore -v`, hooks (`pre-commit`, `pre-push`) | Phase 9 |
| সিকিউরিটি | `commit -S`, `verify-commit`, `credential fill`, `filter-repo` | Phase 10 |
| GitHub ওয়ার্কফ্লো | `gh pr create`, branch protection, GitHub Actions YAML | Phase 11 |
| ইমার্জেন্সি প্লেবুক | wrong-branch fix, force-push রিকভারি, `fsck`+`repack` | Phase 12 |

সম্পূর্ণ, ব্যাখ্যাসহ ৩০-৪০টা কমান্ডের এক্সটেন্ডেড রেফারেন্স টেবিল Module 39-এর প্রথম leaf-এই আছে।

## Appendix B — রিসোর্স লিস্ট

- **Pro Git বই** (git-scm.com/book) — ফ্রি, অফিসিয়াল, সবচেয়ে নির্ভরযোগ্য গভীর রেফারেন্স।
- **git-scm.com/docs** — প্রতিটা কমান্ডের অফিসিয়াল man page, ফ্ল্যাগ-বাই-ফ্ল্যাগ।
- **GitHub Docs** (docs.github.com) — fork/PR/Actions/branch-protection-এর মতো প্ল্যাটফর্ম-স্পেসিফিক ফিচারের জন্য।
- **git-filter-repo ডকুমেন্টেশন** — সিক্রেট রিমুভাল/হিস্ট্রি রিরাইটের জন্য অফিসিয়াল রিপ্লেসমেন্ট টুল হিসেবে `filter-branch`-এর বদলে।

## Appendix C — এই কারিকুলাম কী কভার করে না

- Bazel/Pants-এর মতো ডেডিকেটেড মনোরেপো বিল্ড টুলিং — Phase 8-এ শুধু Git-নেটিভ মনোরেপো টুল (sparse-checkout, partial clone) কভার করা হয়েছে।
- অ্যাডভান্সড CI/CD পাইপলাইন ডিজাইন (multi-stage deployment, canary release ইত্যাদি) — Phase 11-এ শুধু GitHub Actions-এর বেসিক পরিচিতি আছে।
